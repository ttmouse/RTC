# RTC 验证角色与隔离（A3 实例）

> 本文件写明：在 RTC 这个项目里，谁担任哪个角色、靠什么隔离。
> 隔离铁律：**同一 Agent 实例或同一上下文 MUST_NOT 同时承担 BUILDER 与 CHALLENGER。**

## 本项目实况

RTC 是一个**单人产品项目**：douba 是产品负责人，AI 承担实现与验证。因此角色分配的现实形态是：

- **人类只做两件事**：开工前审「能力问题清单」，完工后审「验收总表」。中间过程全部交给机器。
- **AI 靠上下文隔离**实现 BUILDER / CHALLENGER 分离，而不是靠不同的人。

## 角色矩阵

| 角色 | 谁 | 允许输入 | 允许输出 | MUST_NOT |
|---|---|---|---|---|
| ORCHESTRATOR | Cindy / Claude Code 会话主上下文 | 全部 | 摘要、状态、公开结果 | 修改验证原始结果 |
| SPECIFIER | **douba（人类，产品负责人）** | 产品意图、用户反馈、现有文档、真实事故记录 | 能力问题清单、目标/反目标、风险分级 | 把未知项推断为已确认事实 |
| BUILDER | AI 子上下文 A（实现改动） | 已冻结的公开规格与公开测试 | 源码、构建产物 | 读取隐藏挑战；修改产品原则或验证阈值 |
| CHALLENGER | AI 子上下文 B（**与 A 不同上下文**） | 能力问题清单、风险清单、ux-issue-log 历史事故 | 挑战用例、反例设计、故障计划 | 读取 BUILDER 的推理记录 |
| VERIFIER | 自动化检查 + 人工实测 | 候选产物、固定工具链 | 原始结果与结构化证据 | 修改产物或「重跑到绿」 |
| SKEPTIC | code-review-graph 代码图 | 代码图、git 历史、证据缺口 | 排序、异常、候选规则 | 直接改变 claim 状态 |
| ATTESTOR | **douba（人类，最终签字）** | 摘要、原始结果 | 签字放行 / 拦截 | 生成缺失的原始证据 |

## 本项目可用的验证工具链（VERIFIER 的固定工具）

| 工具 | 命令 | 能证明什么 |
|---|---|---|
| 静态装载检查 | `npm test`（内含 `check-static.mjs`） | 文件在不在、模块语法对不对、相对导入解析得到吗、HTML 引用的资源存在吗 |
| 状态机单测 | `tests/main-status.test.mjs` | 状态分支落点（空闲/录音 × 服务状态） |
| 服务恢复单测 | `tests/model-recovery.test.mjs` | 日志→人话翻译、Rust 命令注册名对得上 |
| 音频恢复单测 | `tests/audio-recovery.test.mjs` | 睡眠唤醒后的判断逻辑 |
| 按键/指令单测 | `tests/app-rule-lists.test.mjs` | 应用名单匹配语义 |
| VAD 单测 | `tests/vad.test.mjs` | 噪声校准与阈值 |
| 时间分组单测 | `tests/time-grouping.test.mjs` | 微信式时间分组规则 |
| 界面几何巡检 | `npm run check:ux` | 内容被裁掉、控件点不动、对比度、横向溢出（真浏览器量几何） |
| 音频管道巡检 | `npm run check:audio` | 装上之后的行为：断了会不会自愈、救不回来会不会如实报 |
| 名字体检 | `npm run check:js` | 漏 import / 错导出名（症状是功能静默失效） |
| 代码图 | `code-review-graph`（CLI，非 MCP） | 实现图、影响面、死代码、社区结构、执行流 |

**盲区登记（这些工具的结论不得单独用作门禁）**：
- `check-static.mjs` 只证明「代码装载得起来」，对「跑起来之后长什么样」一无所知（UX-1 在它眼里是完美代码）
- `check:ux` / `check:audio` 需要 Playwright，**不在仓库依赖里** —— 缺了会跑不起来，不是「通过」
- 图工具对反射 / 动态代码有静态抽取盲区
- **UX-2 / 5 / 6 / 7 / 8 这类要读内容语义的（时间戳对不对、单位一致不一致、两个数字能不能比），机械脚本判定不了** —— 目前靠人工加 ux-issue-log 记账
- 浏览器巡检复现不出 WKWebView 特有的 `AudioContext.state = 'interrupted'`（Chromium 没有这个状态），真机合盖-唤醒只能在真机上量

## R2/R3 的额外隔离要求（对应 project.yaml 的 should）

- BUILDER 与 CHALLENGER 使用**不同上下文**（本项目已满足：双清单独立生成，互不可见）
- 理想情况使用不同模型减少共同偏差
- 结论层面的**最终判断权**保留给人类（douba），AI 不得自行宣布放行

## 人类闸门（douba 只读两样东西）

1. **开工前**：审能力问题清单（业务层）—— 确认「还有没有漏」
2. **完工后**：审验收总表 —— 签字放行 / 拦截
