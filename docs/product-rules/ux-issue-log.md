## 怎么区分「已修」和「待定」

- **已修** —— 改完了，并且有**能变红**的检查守着（单测 / 巡检脚本 / 浏览器实测数字）。
  只写「已修」而没有守门检查的，一律降级成「待定」。
- **待定** —— 已确认现象是真的，但**要不要改、改成什么样需要产品判断**，不能由实现方替用户决定。
- **已否决** —— 讨论后决定这是刻意为之，把理由写下来，免得下次又当 bug 提一遍。

## UX-1 ｜ AI 那一档的正文滚不动，一万多像素的会议内容被裁掉

**状态**：已修（2026-09-17）｜**位置**：会议白板

**现象** 白板「AI 会议内容」那一档，正文只看得见上半屏，滚轮怎么滚都不动。逐字稿那一档正常。

**证据**（修之前，浏览器实测）

```
div.editor-canvas   clientHeight=770   scrollHeight=15854   overflow-y=hidden
滚轮后: window.scrollY 0 -> 0;  .milkdown-host scrollTop=0
```

页面滚不动（`.board-wrap` 已锁成 `height:100vh; overflow:hidden`），编辑器自己也没有滚动容器
（`.milkdown-host` 的高度和滚动指望上游挂的 Tailwind 类 `h-full` / `overflow-auto`，
而这个构建里**没有 Tailwind**），于是 15000px 正文被 `.editor-canvas` 的 `overflow:hidden` 整段裁掉。

**为什么是问题** 这不是「不好看」，是**用户拿不到自己的内容**。而且它长得完全不像坏了——
界面没有任何异常，只是下半截不存在。

**修法** 给编辑器自己的滚动容器补上高度和滚动（`meeting-board/src/style.css`）：

```css
.editor-wrap .milkdown-host{ height:100%; overflow-y:auto; padding:12px 24px 80px; }
```

**守门检查**（两个，都验证过「改回去就会红」）

- `meeting-board/tests/editor-scroll.test.mjs` —— 断言「页面锁成一屏高时，两档内容必须各自可滚」。
  把修复回退后：`2 passed, 3 failed`，退出码 1。
- `npm run check:ux` —— 用浏览器真量几何，回退后报
  「内容被裁掉且够不着：纵向还有 7324px 看不到（clientHeight=770, scrollHeight=8094）」。

## UX-2 ｜ 逐字稿的时间戳是**编出来的**

**状态**：待定｜**位置**：会议白板 · 逐字稿那一档｜**影响**：数据可信度

**现象** 每条逐字稿前面的 `[HH:MM]` 看着像真实时间，其实是按段序号在整场时间轴上**均匀插值**出来的。

**证据**（同一场会议内 5 条记录，真实间隔故意做得不均匀）

| 事件 | 真实间隔 | 真实时刻 | 页面显示 | 对得上 |
|---|---|---|---|---|
| 1 | 0s | 21:04 | 21:04 | ✓ |
| 2 | 5s | 21:04 | **21:05** | ✗ |
| 3 | 10s | 21:04 | **21:06** | ✗ |
| 4 | 100s | 21:06 | **21:07** | ✗ |
| 5 | 290s | 21:09 | 21:09 | ✓ |

**真实发生在 21:04 的三条，被显示成 21:04 / 21:05 / 21:06。**

**为什么是问题** 它违反第 2 条「状态必须真实」。用户拿这个时间戳去对「谁在什么时候说了什么」，
得到的是一个编出来的答案——而且**没有任何迹象表明它是估算的**。
会议里最常问的就是「这个结论是几点定的」，这条线索现在是错的。

**根因** `server.js` 的 `detectSessions` 把事件压成 `texts: string[]`，每条事件的 `ts` 在这一步丢了；
`formatTranscriptLines` 只能按序号铺时间。数据本来就有，是中途丢的。

**要产品判断的** 修成真实时间之后，同一分钟内的连续多句会显示成同一个时刻（`[21:04]` 重复好几行）——
这比现在「每行都不一样」更真实，但更难看。是接受重复，还是改成「间隔超过 N 分钟才标一次时间」？

## UX-3 ｜ 白板的次要文字对比度全线低于可读线

**状态**：待定｜**位置**：会议白板（所有状态）

**现象** 白板里所有「次要文字」——注释、状态、标签上的计数——都偏淡。

**证据**（`npm run check:ux`，4 场景 × 3 视口 × 2 标签，24 个组合全中，共 84 处）

| 元素 | 颜色 | 对比度 | 字号 | 可读线 |
|---|---|---|---|---|
| `.preliminary-note` 注释 | `#aaa196` on `#faf9f7` | **2.42:1** | 11px | 4.5:1 |
| `#preliminaryStatus` 状态 | `#9a9287` on `#faf9f7` | **2.92:1** | 11px | 4.5:1 |
| `.preliminary-tab` 未选中标签 | `#9a9287` on `#faf9f7` | **2.92:1** | 13px | 4.5:1 |
| `.preliminary-tab-count` 计数 | `#8b8276` on `#ece8e2` | **3.10:1** | 10px | 4.5:1 |

> 两点后续变化，读数不再等于现状：
> `#preliminaryStatus` 一行已随 UX-10 作废（元素本身已删，不再展示）；
> `.preliminary-note` 仍在，但只在**没有内容**时出现，覆盖面比当初小。
> 数字口径：2026-09-17 修完 UX-10 后重跑 `npm run check:ux`，从 54 处降到 48 处（只少了状态文案那一档）。

**为什么是问题** 4.5:1 不是外部标准塞进来的——`ui-interaction-spec.md` 附录自己就写着
「色带压过来会把刻度对比度从 5.19 拉到 3.07（**低于 4.5 可读线**）」，并且当时是当作 bug 修的。
同一把尺子，主界面和白板的次要文字都没过。

**主界面有同样的问题**（`--ink-faint #8f8572` on `--paper #f3ede2` = 3.13:1）：
`.listHint`「更早没有记录了」、`.empty`「今天暂无记录」、`#meterReadout`。

**要产品判断的** 这是一种刻意的「淡」。要么承认它就是刻意的、把 4.5 线从规范里去掉（但那样
UX-3 就该标成已否决），要么承认 4.5 线算数、把 faint 系列整体调深一档。**不能两边都要。**

## UX-4 ｜ 白板是一套**独立的外观**，不受共享调色板约束

**状态**：待定｜**位置**：会议白板

**现象** 白板看起来不像主界面的一部分：主界面是米黄纸色（`--paper #f3ede2`），白板是纯白（`#faf9f7`），
文字用的是中性灰（`#999` / `#666` / `#555` / `#2c2c2c`），还多了一个**黄色**强调色 `#c9a227`（用在整理失败态）。

**证据**

```
meeting-board/src/style.css: 写死颜色字面量 89 处
                             使用共享调色板变量 var(--ink/--paper/--seal)  0 处
```

白板是独立 HTML 入口（`meeting-board/index.html`），只加载自己的 `theme/` 与 `style.css`，
**不加载** 主界面那份定义 `:root` 调色板的 `src/css/style.css`。

**为什么是问题** 两条明文约束：

1. `ui-interaction-spec.md` 附录：「颜色全部定义在 `src/css/style.css:1-6` 的 `:root`，
   **不要在组件里写死颜色**」——白板 100% 写死。
2. 规范第 1 条：「只有**一个**强调色：印章红……别的地方不要用」——
   白板引入了第二个（黄 `#c9a227`），而且规范里「用一次就不珍贵了」说的正是这种稀释。

**要产品判断的** 白板是投给一屋子人看的那块板，**故意做成纯白高对比**是站得住的（投影仪上纸色发灰）。
如果是故意的，就把这条标成已否决并写进规范；如果不是，白板需要接进共享调色板。
顺带：黄色那个新强调色无论哪种情况都要单独决定去留。

## UX-5 ｜ AI 那一档空着时，露出编辑器自己的骨架「无标题」「目录 0」

**状态**：待定｜**位置**：会议白板 · AI 会议内容那一档（未生成 / 生成失败 / 还没写）

**现象** 状态说明是对的（「生成失败」，并解释了原因），但**正文区域**同时显示编辑器自己的空文档骨架：

```
756x65  top=150  .omia-page-title-placeholder  「无标题」
（同一区域还有「☷」拖拽柄和「目录 0」大纲按钮）
```

**为什么是问题** 两块内容在互相打架：下面一行说「本地模型没跑成功」，上面一块 65px 高的地方写着
「无标题」。用户看到的是**一个打不开的空文档**，而不是「这里本来就还没有东西」。
「目录 0」更是纯粹的编辑器内部概念，白板用户不需要知道。

**建议方向** 空态时不要挂载编辑器正文，或者把正文区整个让给空态说明。
（注意：`visibility` vs `display:none` 那条约束——编辑器挂载时要能量到高度——在**有内容**时才适用；
空态根本没有内容可量。）

## UX-6 ｜ 标签宽度会随内容出现而跳动，用户正指着它的时候

**状态**：待定｜**位置**：会议白板 · 标签栏

**现象** 两个标签各带一个计数。内容一到位，计数一出现，标签就变宽。

**证据**（浏览器实测）

```
空着:   {'raw': 68, 'ai': 68}
有内容: {'raw': 68, 'ai': 96}      → AI 标签 68px → 96px，一次跳 28px
```

**为什么是问题** 跳的时机恰好是「AI 刚整理完」——用户很可能正盯着、正要点它。
规范第 3 条专门写过「视觉位置必须停在原处，不能跳一下」，那条讲的是列表，这里是同一类毛病。

## UX-7 ｜ 两个标签上的数字不是同一个单位，并排摆着像可以比

**状态**：待定｜**位置**：会议白板 · 标签栏

**现象** 标签实际渲染成 `逐字稿40` 和 `AI 会议内容41`。

- `逐字稿 40` = **40 条**转写记录
- `AI 会议内容 41` = **41 行**正文

**为什么是问题** 并排两个数字，用户默认它们可比（「AI 把 40 条整理成了 41 行」），
实际一个数「条」、一个数「行」，两个数之间没有任何关系。
而且数字和文字之间没有间隔，`逐字稿40` 读起来像一个编号。

**建议方向** 要么统一单位（都用「条/段」），要么给数字一个说得清的标签（「40 条转写」「41 行」），
要么干脆去掉 AI 那一档的计数。

## UX-8 ｜ 整理在后台跑的时候，AI 那一档不说「正在生成」

**状态**：待定｜**位置**：会议白板 · AI 会议内容那一档

**现象** 「生成中…」这个状态只在**本页面自己点了整理**的时候才出现：
`preliminaryPending` 是页面里的一个变量（`meeting-board/src/main.js`），
请求发出去时置真、拿到结果置假。

**为什么是问题** 整理还可能由别处触发（另一个窗口、或页面中途刷新）。
那些情况下服务端其实正在整理，但白板只会说「还没有内容」——**把「正在干活」说成了「什么都没有」**。
规范第 2 条：「状态必须真实」，这几个字是用户判断「还要不要等」的唯一依据。

**建议方向** 服务端已经在 `preliminary.status` 里区分 `pending`；让前端也认这个字段，
而不是只看页面自己的变量。

**状态**：待定（低）｜**位置**：会议白板 · 顶栏

## UX-10 ｜ 白板的标签栏里挂着自己的「说明」

**状态**：已修（2026-09-17）｜**位置**：会议白板 · 标签栏（顶部 Tab 区域）

**现象** 标签栏右侧固定挂着一行状态文案，随内容变化：

```
AI 档（白板正文） : 「逐字稿 40   AI 会议内容 41   可直接编辑」
AI 档（本地模型垫的）: 「… 本地模型 · minicpm5-meeting」
逐字稿档           : 「… 未整理」
```

用户的原话：**「白板里的这类文案不要展示，最起码也不应该展示在顶部 Tab 区域。」**

**为什么是问题** 这行字在屏幕上**最显眼、离内容最远**的位置（标签栏最右），说的却是内容自己的事：

- 「可直接编辑」——**顶栏的「编辑」按钮已经在说这件事**，而且那个是真能点的；文字版既不能点又占位置。
- 「本地模型 · minicpm5-meeting」——模型名是内部实现。用户不需要知道这版是哪个模型垫的（对照 `ui-interaction-spec.md` 第 1 节「白板是投给一屋子人看的那块板」）。
- 另一个副作用：它把标签栏变成了「两档标签 + 一段随状态变长变短的说明」，而规范第 3 条
  专门写过「视觉位置必须停在原处，不能跳一下」（UX-6 是同一类病）。

**修法** 不是把这行字搬到别处，而是把「有内容时不需要解释」当规则：

1. 标签栏里**只留两档标签**，`#preliminaryStatus` 连同它的 CSS 一起删掉。
2. `resolveTabView` 不再产出 `status` 这一栏（结构上就没有可搬回标签栏的东西）。
3. 有内容的那一档 `note` 为空，连元素一起 `hidden`（不留一条空白带占内容的高度）；
   只有**没内容**时才在内容区底部写一句：在等什么 / 为什么没出来（生成中 / 生成失败 / 暂无转写）。

**守门检查**（三道，均验证过「改回去就会红」）

- `meeting-board/tests/preliminary-panel.test.mjs` —— 断言「有内容就只给内容」：
  `document` / `analysis` / `local` 三种出处、以及逐字稿那一档，`note === ''`；
  并且 `view.status === undefined`。顺带拿源码断言标签栏模板里只有 `preliminary-tabs`。
  把 `<span class="preliminary-status">` 加回标签栏后立刻 `76 passed, 2 failed`。
- `npm run check:ux` —— 重跑巡检，`span#preliminaryStatus` 从报告里消失，
  发现数从 54 处降到 48 处（降的全是这行字自身的对比度告警）。
- 人眼：对 4 个场景 × 2 档截图确认标签栏只剩标签（改前/改后都截过）。

**没动的**：`fallback` 时标签下划线的黄色强调色还在（它标的是「这一档没内容、是失败的」）。
去留归 UX-4 一起判断，别顺手删。

**后记（2026-09-30）** 白板 AI 整理从本地硬编码模型改为用户配置的 AI（ADR-004）时，
按钮与空档/失败文案里残留的模型词一并清掉：按钮改名「生成纪要草稿」，
fallback 注记去「本地模型没跑成功」改为「AI 起草没跑成功」，
empty 注记改为指路按钮；巡检 fixture 的 `model: 'minicpm5-meeting'` 与
`error: 'Ollama 整理超时'` 同步更新。同病根，不新开编号。

## UX-11 ｜ 本机模型服务没跑，主界面照样说「就绪」

**状态**：已修（2026-09-17）｜**位置**：主界面 · 底部状态区

**现象** 本地引擎（SenseVoice / Qwen3）的识别还依赖**第二个服务**——本机的模型服务
（`asr_local/server.py` 一个进程同时提供 8932 识别 WS 和 8933 模型管理 HTTP）。它没起来时：

- 设置页 →「识别方式」那一行如实写着「**使用中 · 模型服务未启动**」；
- 主界面底部状态区写的是「**就绪**」，点和字都是常态色，看不出任何异常；
- 点录音也不会被拦，要等 **15 秒** ASR 连接超时之后才弹一句话并停止录音。

**证据**（本机实测，8932 / 8933 都没起、只有 8931 在跑）

```
$ lsof -nP -iTCP -sTCP:LISTEN | grep -E "8931|8932|8933"
node 83803 douba ... TCP 127.0.0.1:8931 (LISTEN)        ← 只有代理服务在
$ curl -s -m 2 http://127.0.0.1:8933/model/status       ← 空（连接被拒）

主界面状态区：就绪              （修之前）
设置页引擎行：使用中 · 模型服务未启动
```

**为什么是问题** 这是 `core-product-principles` 第 3 条（界面上每个状态只能有一个「真实来源」）
和规范第 2 节那条硬约束——「空闲状态 + 服务连不上时，**不许显示「就绪」**」。
用户看到「就绪」就放心开录，开完才发现一个字都没有。

之前只把「代理服务（8931）不可达」接进了状态机，漏了「本地引擎还依赖第二个服务（8933）」。
结果是设置页知道、主界面不知道，两个页面各说各话。

**修法**

1. `src/js/model.js` 新增 `probeModelService`：探测 8933，结论写进 `state.modelServiceOk`
   （只有本地引擎才可能为 `false`，百炼一律 `null`）。设置页的 `renderModelStatus`
   和主界面看护循环都走它 → 两处永远是同一次探测的结论。
2. `src/js/ui.js` 的 `computeRunStatus` 增加第七种说法「**模型服务未启动**」
   （告警色 + `data-tip` 指路设置页），空闲态与录音中都覆盖。
3. 点录音时若已确认模型服务未启动，直接一句话拦下，不再空等 15 秒超时。
4. 判定刻意加了冷启动宽限（20 秒）＋连续两次失败才报异常：应用刚起来时 python 侧
   还在加载依赖与模型，那会儿连不上是正常的，不能让开局闪一个假警报。
   服务起来后 5 秒内自动转回「就绪」。

**守门检查**（验证过「改回去就会红」）

- `tests/main-status.test.mjs`（已接进根目录 `npm test`）—— 钉住状态机的分支：

## UX-12 ｜ 「模型服务未启动」是条死路：没有原因，也没有把服务弄回来的入口

**状态**：已修（2026-09-17）｜**位置**：设置页 ·「识别方式」

**现象** UX-11 让状态说了真话，但真话只有四个字。设置页引擎行写着「使用中 · 模型服务未启动」，
下面是三张引擎卡片——没有原因、没有按钮、没有命令。主界面状态区的悬停提示却写着「打开设置 →
「识别方式」可以看到原因和修复命令」，而那句承诺在「服务整个没跑」这条路径上兑现不了
（「修复命令」只有「服务活着但缺 python 依赖」那条分支才有）。用户唯一能做的是退出重开应用；
如果原因是缺依赖或者端口被占用，重开多少次都一样。

**为什么是问题** 报出问题不等于给出去路。用户看到这四个字只会想「那我该怎么办」，
界面必须回答「为什么」和「怎么办」，否则就是把用户丢在死路上（core-product-principles
第 3 条补的那段就是这条：说出了问题，就要给出下一步，而且承诺的入口必须真的存在）。

**修法**

1. Rust（`src-tauri/src/lib.rs`）：本机 ASR 服务的 stderr 除了打控制台，还进一个 80 行的环形缓冲；
   新增两条命令——`local_asr_status`（进程还在不在、是不是本应用启动的、日志尾部）和
   `restart_local_asr`（杀掉自己起的进程 → 等端口放开 → 重新拉起 → 等 8933 就绪，最多 30 秒）。

   可展开的服务日志。
3. 状态一变就重渲染：服务自己回来（或又挂掉）时，开着的设置页不能停在旧结论上。

**证据**（浏览器实测：用 `ctx.route` 把 8933 断掉模拟服务不在 + 桩 `__TAURI__` 走桌面端那条分支，
不碰本机正在跑的服务。当时的一次性实测脚本已随临时文件清理删除，判定逻辑沉淀在下面的守门检查里）

## UX-13 ｜ 缺依赖时那条「照这行命令装一下」的提示，根本渲染不出来

## UX-14 ｜ 合上盖子再打开：界面一切正常，录音却一个字都出不来

**状态**：已修（2026-09-17，真机复验待做）｜**位置**：录音链路（麦克风 → 音频会话 → ASR 连接）

**现象** 笔记本睡眠唤醒之后，应用看起来完全正常：状态区写着「就绪」，点录音进「识别中」，
电平尺也在动。但实际上一个采样都没有离开这台电脑——录一整场，事后发现什么都没存。
用户唯一能自己弄回来的办法是**退出重开应用**。

**为什么它比「明着报错」更糟** 这条违反第 3 条产品原则（状态必须真实）最狠的一档：
它不是没状态，而是**状态和事实相反**。而且它长得跟好用的时候一模一样，用户没有任何理由怀疑。

**候选根因（按可能性排）**

1. **WebAudio 会话在睡眠里被打断**。WebKit 会在系统睡眠、或音频会话被别的应用抢走之后，
   把 `AudioContext.state` 置成它特有的 `'interrupted'`（而不是 `'suspended'`）。
   旧代码只对 `'suspended'` 调 `resume()`，于是这个状态下音频图整个是哑的：麦克风回调一次都不触发。
   这也解释了「为什么只有重开应用才行」——同一个页面里再新建上下文同样起不来。
2. **麦克风句柄失效**。唤醒后 macOS 可能让旧设备句柄失效（音轨 `ended`），
   而代码只判断 `!state.stream`，于是老老实实复用了那条死流。USB 麦克风/耳机重新枚举后尤其容易。
3. **ASR 的 TCP 连接看起来还开着**。睡眠会掐断它，但 `readyState` 仍可能是 `OPEN`，
   音频发出去就掉进黑洞。

**修法（三层，都指向「不要相信看起来还开着的东西」）**

- 音频会话不 running 就必须拉回去，`interrupted` 与 `suspended` 同等对待；拉不回来**抛错**，
  不假装还能录（`audio.js` 的 `audioStateAction` / `ensureAudioRunning`），并挂上 `onstatechange`
  自愈——录音中途被抢走也会自己回来。
- 取麦克风之前先问旧流死没死（音轨全 `ended` = 重取），并加了**音频流动看护**：
  录音时麦克风回调停满 3 秒 = 管道断了（**判据是结构性的回调停了，不是「安静」**），
  先自动重建一次音频输入；还不行就报「没有声音输入」。
- 认出「睡过一觉」并主动重建：浏览器不给 `lid` 事件，所以用**自己的定时器跳变**认
  （跳超过 5 秒 ⇒ 中间睡过）；正在录音就重建麦克风并重开 ASR 连接，同时立刻重探两个服务，
  不等下一次 60 秒校准。定时器被遮挡节流也会误判，所以唤醒动作全部便宜且幂等。

**守门检查** 两个，都跑过、都是绿的：

- `tests/audio-recovery.test.mjs`（22 项，进 `npm test`）——钉判断逻辑。已证明**会变红**：
  把 `interrupted` 从可恢复状态里去掉、把「没有声音输入」分支删掉、把 `watchWake` 的调用删掉，
  分别报出对应的失败项，退出码 1。
- `npm run check:audio`（`tests/audio-pipeline.browser.mjs`，真浏览器）——钉装上之后的行为：
  真 MediaStream 发音频 → 把音频会话全部关掉（睡眠干的事）→ 必须自动重建并重新出声；
  持续关掉会话 → 必须报「没有声音输入」；取不到麦克风 → 必须报「麦克风不可用」。
  麦克风用振荡器、ASR 用本地假引擎，不碰真实麦克风，也不写任何真实记录。9 项全绿。

**顺带修的** 这个巡检第一次跑就抖出一个老问题：连上就在怀里停录/重连时，旧连接的迟到消息
（`connected`）会去读 `state.asrWs`——那时它已经是 null 或下一条连接，控制台一条 TypeError，
没人知道它坏了。现在 `connectASR` 的四个回调都只认自己那条 socket（状态也只在「还轮得到我」
时才写），对得上「等待之后要重新确认对象身份」那条规则。

**还没证到的** 真实的合盖-唤醒这条路只能在真机上量：本机无法在不真睡的前提下复现 WebKit 的
音频中断（浏览器巡检验的是同一类故障下的自愈与诚实，Chromium 没有 `interrupted` 这个状态）。
待用户合盖复验的一次就是它的最后一关。

**守门检查** `tests/manual-hallucination.test.mjs`（7 项，进 `npm test`）——驱动真实 python 会话对象，
`recognize` 用替身（不加载模型）：1 秒静音不上屏、单帧 32ms 脉冲不上屏、500ms 与 100ms 说话保留、
静音的人声证据不带进下一段、常态录音两条不受影响。**已证明会变红**：把判据改成恒真后，两条空按用例
失败、退出码 1；还原即绿。

**还没证到的** 用的是合成音频（正弦 + 静音），不是用户麦克风的真实底噪；若用户把刻度调到让环境噪声
也能过阈值，空按仍会漏过——这一档只能靠实机复验。

## UX-17 ｜ 百炼模式下说一句话，列表里冒出好几条越来越长的记录

**状态**：已修（2026-09-20，打包版待用户复验）｜**位置**：百炼识别（前端静音兜底）

**现象** 百炼引擎下说一句完整的话，列表留下多条记录，每条都是上一条的加长版，中间几条没有标点、
最后一条才带句号。用户 2026-09-20 23:35 的实测截图里一句话 4 行，且这 4 行一律显示「没粘出去」。

**证据与根因**

- 记录的时间戳会说话：`events/2026-09-20.jsonl` 里 15:35:10.669 → 12.035 → 14.498（UTC）三条，
  前两条间隔 **1.366 秒**；`events/2026-09-19.jsonl` 15:48:56.257 → 57.622 间隔 **1.365 秒**；
  15:48:57.622 → 58.xxx 同为 1.365 秒。这种精确重复只能是代码里的固定计时器。
- 计时器就是前端自己的静音兜底（修之前 `src/js/asr.js`）：百炼路径下 
  `Int16 域 RMS < SILENCE_THRESH(300)` 连续 `SILENCE_FRAMES(16)` 块就 `finalizePending()`；
  音频块来自 `createScriptProcessor(4096)` 的回调（≈85ms/块），16 块 ≈ **1.365 秒**。
- 为什么它会“提前”：百炼的中间帧是**累积文本**（同一句越来越长），而这道兜底只看音量不看语义，
  用户说话轻、语音中间低下去一段，半句就被当成说完了。
- 直连百炼对照实验（`qwen-audio-3.0-asr-flash-streaming`，只读探测，未入库）：中间帧
  `end_time=null` + `sentence_end=false`，只有真句尾才 `end_time>0` 且 `sentence_end=true`；
  把音频压到 RMS≈203（低于 300）后它照样一字不差地识别、照样只在真句尾给 final。
  也就是说这道兜底既非必需，又比百炼更早更激。
- 两条规则同时被绕开：主界面刻度（用户设 0.0015，≈Int16 域 49）与写死的 300 相差 6 倍且不受界面控制
  （见 [D-009](../../project-ledger/records/D-009-vad-single-threshold.md)「主界面刻度是唯一实际生效的识别阈值」）；
  而 `ui-interaction-spec` §2 本来就写明按住说话期间不应用音量阈值、静音断句，
  这道兜底却不区分 `pushToTalkManual`。

**为什么是问题** 用户拖灵敏度怎么拖都没用（他拖的是另一个门槛）；记录被拆条污染，历史与统计跟着错；
抢存这條路不走粘贴流程，所以真实粘出去了也会被记成「没粘出去」；切引擎的一瞬间抢存，
还会把百炼的内容记到新引擎名下（本次 4 条里就混进一条 `engine=sensevoice`）。

**修法** 百炼模式删掉「按音量提前定稿」：移除 `checkSilence`、两个常量、`state.silenceChunks` 及其复位；
句尾交还百炼自己的 VAD（实测句末到最终结果只差 0.1~0.2 秒）。这也顺带满足了「按住说话不抢存」。
保留的是另一个门槛——决定「这段声音要不要发出去」的主界面刻度（百炼按音频时长计费，那个闸门不能删）。

**守门检查** `tests/vad.test.mjs` 新增两条静态断言（不许出现 `checkSilence` / `SILENCE_THRESH` /
`SILENCE_FRAMES`，`state` 不再保留 `silenceChunks`），进 `npm test`。
**已证明会变红**：临时把 `const SILENCE_THRESH = 300;` 加回 `asr.js`，该用例失败、退出码 1；删除后即绿。

**还没证到的** 真机复验要看用户重打包后的实录——本机上原来的录音无法重放，低电平的判定
（用户当时是不是真的说轻了）是由 1.365 秒的精确间隔反推的。

## UX-18 ｜ 关掉会议白板那个小窗口，整个后端服务跟着消失

**状态**：已修（2026-09-30，静态守卫就绪；桌面端行为复验待做）｜**位置**：Tauri 壳 · 窗口关闭与本地服务托管

**现象** 看完白板顺手关掉那个独立小窗口，主界面立刻变成「连接异常：无法连接到本地代理服务 (ws://127.0.0.1:8931)」。
之后界面每次自动重连都被拒，一个字也进不来。

**证据与根因**

- 2026-09-30 排查：主进程（`rtc-transcriber`）还活着，后端 sidecar（`node-server`，PID 3815）在 **21:55:04** 之后消失。
  `events/2026-09-30.jsonl` 的落盘记录停在 21:51:29，此后 11 分钟空白。
- 系统里**没有**该进程的 crash report、没有 SIGKILL/SIGTERM 记录，也没有它的 stderr——
  打包后的 `.app` 从访达启动时根本没有 stderr 通道（这正是下面「日志落盘」那条要修的）。
- 根因在 `src-tauri/src/lib.rs` 的 `WindowEvent::CloseRequested`：它**不区分窗口**，
  任何窗口被关掉都无条件 `cleanup` 掉全局的 node/asr sidecar。会议白板是独立窗口
  （`label = meeting-board`，由 `src/js/main.js` 用 `new WebviewWindow` 打开），
  于是「关掉一块查看用的面板」等于「把 8931 后端整个关掉」。
- 为什么本地识别没跟着死：这一轮它是**复用**来的（`asr_reused`），不在 App 名下，
  所以躲过了那次误杀，`state.asr_server` 是 `None`、cleanup 拿不到句柄。

**为什么是问题** 违反产品原则 0——用户以为还在记录，实际上说过的话一个字都不会存下来；
而且这是用户完全无法理解的因果：关掉的明明是个「看板子的小窗口」，坏的却是录音本身。
用户 2026-09-30 的原话是「最近自然总是会自己掉，断掉」。

**修法**（三条，对应 [ADR-005](../decisions/ADR-005-service-follows-app-process.md)）

1. `CloseRequested` 只存窗口尺寸，**不再停服务**；真正的退出走 `RunEvent::ExitRequested` / `Exit`。
2. 后端加看护线程：以「8931 端口通不通」为判据，没了就补，失败按 3s→6s→12s→…→30s 退避；
   退出时先置 `shutting_down`，免得 App 退出了端口还占着。
3. 两个 sidecar 的 stderr 写到数据目录 `logs/{node,asr}-sidecar.log`（2MB 轮转），
   下次异常退出至少留下最后一句遗言和文件 mtime。

**守门检查** `tests/sidecar-lifecycle.test.mjs`（进 `npm test`）四条静态不变量：
关窗口块内不许出现 `cleanup_server`；退出路径必须立 `shutting_down`；
必须存在并真正启动 `spawn_node_watchdog`、且判据是端口；两个 sidecar 都必须有 `open_sidecar_log`。
**已证明会变红**：临时把 `cleanup_server(&window, "node")` 加回关窗口块，用例失败、退出码 1；还原后即绿。

**还没证到的** 静态守卫只证明「伤人的写法不在代码里」，证不了「关掉白板窗口后 8931 一定还在」——
那要在桌面端真的开一个白板、关掉、看主界面是否继续可用（`lsof -iTCP:8931` 仍在听）。
另外当晚后端到底是「被关窗口连带杀掉」还是「自己退出」，因为没有日志仍然无法 100% 定案：
证据指向后者更可能（复用来的识别服务活着），但这正是第 3 条要补上的空白。

## UX-19 ｜ 面板「生成纪要草稿」看不见用户手写的内容

**状态**：已修（2026-09-30，待重打包复验）｜**位置**：会议白板 · 生成纪要草稿（`POST /api/meeting-board/preliminary`）

**现象** 用户在正文里手写了判断，点「生成纪要草稿」，草稿完全不提这些内容。而同一件事走外部 AI 通道（`rtc board brief`）时，那些手写的行会被单列为「人工锚点」，并被要求原样保留。

**证据与根因** `server.js` 的 `runPreliminary整理` 组提示词时只放了 `transcript`，system prompt 也只说「根据下面的会议逐字稿」。而「哪些行是用户手写的」在 `scripts/board-provenance.cjs` 里是现成的（`boardProvenance()` 读侧判定），只是这条路径没调用它。

**为什么是问题** 违反 ADR-003 的决定 1（AI 生成时参考人工内容，且当锚点）。更麻烦的是**同一个按钮的行为不可预测**：用户在哪个入口生成纪要，决定了他写的话算不算数。

**修法** 面板起草复用 `boardProvenance()` 读侧判定（不重写第二套），把已有正文与人工锚点按 brief 的同套规矩交给 AI：围绕锚点补证据、原样保留原句、矛盾时保留原句并给出处。来源三分支与 brief 一致；写回路径、采纳按钮、失败回退一律不动。见 [ADR-006](../decisions/ADR-006-board-draft-reads-human-anchors.md)。

**守门检查** `meeting-board/tests/preliminary.test.mjs` 新增六条断言：手写正文要进提示词、手写行要标成人工锚点、要写出「原样出现在你的草稿里」、正文为空时不得凭空加一段、AI 写回的正文要如实标成 AI 的、没有人工锚点时不得要求原样保留。
**已证明会变红**：临时把提示词里的 `${sourceBlock}` 摘掉，用例失败、退出码 1（`手写的正文要进起草提示词，不能只喂逐字稿`）；还原后即绿。

**还没证到的** 打包版行为要在重装后复验；正文很长时 token 成本上升多少没有实测数字。

## 附录：为什么以前没有脚本挡住这些问题

**简短回答：确实没有。** `npm test` 跑的是 `scripts/check-static.mjs`，它只做**静态**检查——
文件在不在、模块语法对不对、相对导入解析得到吗、HTML 引用的资源存在吗、Python 能不能编译。

它是一盏**只证明「代码装载得起来」的灯**，对「跑起来之后长什么样」一无所知。
UX-1 那种问题在它眼里是完美的代码：语法没错、资源没缺、页面不报错，
只是 15000px 内容被 `overflow:hidden` 裁掉了。

这一点 `check-static.mjs` 自己的文件头就写过——它上一版是「一盏永远绿的灯」，
当时的问题是「检查的文件根本不存在，却静默跳过」。UX-1 是同一类病的另一个变种：
**检查的东西是真的，但检查的维度不全。**

### 现在有什么

**`npm run check:ux`**（`scripts/check-ux.mjs`）——把页面真的跑起来，用浏览器量几何。
自带夹具起临时服务，跑 4 场景 × 3 视口 × 2 标签 = 24 个组合。退出码非 0 表示有发现，可直接当门禁。

它只查**机械可判定**的毛病，不掺审美判断，因此不会产生「这算不算问题」的扯皮：

| 检查 | 判据 |
|---|---|
| 内容被裁掉且够不着 | 元素内容溢出、被 `overflow:hidden` 裁掉，且祖先里没有任何滚动容器能把它滚出来 |
| 控件被盖住（点不动） | 可点元素中心点被别的元素接走 |
| 控件在视口外且够不着 | 中心点在可视区外，也没有可滚动祖先 |
| 可点区域过小 | 宽或高 < 16px |
| **文字对比度不足** | 正文 < 4.5:1，大字 < 3:1（有效背景色一路往上找，遇到渐变/图片背景就不猜） |
| 大块可见空白 | > 300×200 且自己、后代都没文字也没可点元素 |
| 页面横向溢出 | `scrollWidth > clientWidth` |

**它验证过「会变红」**：把 UX-1 的修复回退、重新构建，脚本立刻报出
「内容被裁掉且够不着：纵向还有 7324px 看不到」，退出码 1。一盏不会变红的灯没有意义，
所以这条是硬要求——新增检查项时必须先证明它能报错。

**还没覆盖的**：UX-2 / 5 / 6 / 7 / 8 这类要读内容语义的（时间戳对不对、单位一致不一致、
两个数字能不能比），机械脚本判定不了，目前靠人工加上本文档记账。
