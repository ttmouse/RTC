# ADR-002: 语音片段按时间切分，应用作为每条记录的语境标签

- Status: accepted
- Date: 2026-09-20
- Owner: RTC product owner
- Scope: 语音事件的记录字段、片段切分、会议整理与后续分析的输入

## 背景

用户提出：不同应用里的语音可能代表不同场景，做整理时不应该混在一起。

核对现状后确认三件事：

1. 每条记录**已经在保存**「说话时的前台应用」快照（事件字段 `activeApp`），主界面记录列表也已有「每行左侧标出说话时的前台应用」的界面规则，并明确它表达「说这句话时你在用哪个应用」，不是粘贴去向。
2. 片段切分（现在叫「会议场次」）只看静默间隔，完全不看应用。
3. 展示层把 `activeApp` 丢了：`detectSessions` 把事件压成 `texts: string[]`，逐字稿只剩文本。

同时需要纠正一个概念：产品里把切出来的每一段连续语音统一叫「会议」，但**它的用途不只有会议纪要**。同一段记录可能被用来生成会议纪要，也可能被用来分析别的内容。切出来的东西本质是「一段连续语音」，命名只是习惯。

## 决定

1. **片段切分只按时间连续性**（静默间隔），不按应用切分。连续说话过程中切换应用是常态，按应用切会把一段完整的话切碎。
2. **每条记录都保留说话时的前台应用**，作为**语境标签**完整存下来、不裁剪。它回答的是「这句话是在什么场景里说的」。
3. **片段本身不预设用途**。「会议」只是其中一种分析目的；不因为「这次不做会议纪要」就丢掉标签，也不因为「它叫会议」就预先排除某些应用的语音。
4. **因此不设「会议专用」的应用排除名单**。哪些内容属于本次分析目的，属于分析时的选择，不属于记录时的裁剪。

## 边界

- 标签是线索，不是判据。应用快照可能为空（网页版、查询失败、对着 RTC 自己窗口说话）。2026-09-20 当天 522 条记录里 485 条有值、37 条为空。不得用应用自动判定「这段算不算会议」。
- 应用身份按系统给的三份名字（显示名 / 包名 / bundle id）匹配，不按手工输入的名称匹配。
- 逐字稿里让标签可见的前提是时间真实（见 `ux-issue-log.md` 的 UX-2 与判断台账 MB-02）；时间不可信时，标签和时间会一起失真。

## 考虑过的替代方案

- **按应用切分片段** — 会把一段连续说话切碎；开会时前台应用本来就在变，切出来的边界没有意义。
- **「非会议应用」排除名单** — 把会议当成唯一用途，等于替用户假设了这段录音该怎么用；而且名单会误杀（有人就是用微信开会）。
- **用应用自动判断这段是不是会议** — 应用身份不可靠，只会给出看起来精确的错误结论。

## 后果

- 展示层：会议白板的逐字稿应带说话时的应用标签，与主界面记录列表同一套图标规则；片段不能再把事件压成纯文本数组，`ts` 与 `activeApp` 要一起留在片段里。
- 分析层：把「哪些内容属于本次分析目的」交给分析时筛选，记录阶段保持完整。
- 命名层：「会议」这一叫法已裁决**暂不改名**（2026-09-20），它是这一层的习惯叫法，不代表用途只有会议纪要；将来引入第二个分析用途时再重算，见判断台账 MB-15。
- 不新增录音源、不放宽音频采集边界（仍以本机麦克风为准，见 [ADR-001](ADR-001-product-positioning.md)）。
