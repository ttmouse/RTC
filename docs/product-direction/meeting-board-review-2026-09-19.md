## 一、这次是怎么判断的

不是「看着不顺眼就记一条」。每条结论必须落到下面四档之一，**四档的差别在于它还缺什么**：

| 档 | 含义 | 缺什么 | 下一步 |
|---|---|---|---|
| **A 接收** | 依据明确（产品原则 / 已实测证据 / 用户明确表态），边界清楚 | 不缺 | 可以进 backlog 排期 |
| **B 待裁决** | 现象成立，但「该不该改、改成什么样」需要产品判断 | 缺一个决定 | 记账本，等人拍板；**实现方不能替用户决定** |
| **C 否定** | 讨论后认定是刻意为之，或前提本身站不住 | 不缺 | 写明理由后关掉，防止下次再当 bug 提一遍 |
| **D 缺信息** | 判断所需的事实还不存在 | 缺事实 | 写清「缺什么、怎么才能拿到」，**不进 backlog** |

判断依据只有四个来源，按可信度排：
1. **已实测的证据**（`npm run check:ux` 的数字、真机复现）。
2. **项目自己的产品原则**（[`../product-rules/core-product-principles.md`](../product-rules/core-product-principles.md)）。
3. **用户明确说过的话**。
4. **外部研究结论**（`ai-meeting-notes-research.md`、Granola 结论）。

**不到第 1、3 条，一条判断不许升进 A 档。** 这是这份文档最要紧的一条规矩——它防的是「AI 觉得应该这样」被当成「用户需要这样」。

> 这套四档和 Project-Ledger 的 `status` 词汇是一一对应的：A = `active`，B = `contested`，
> C = `retracted`（带理由），D = `proposed` + 正文里的「未知」。用同一套词是为了将来真接入时能逐条转过去。

## 二、先把场景摆对：白板有两个模式，不是一个

第一轮分析里我把白板当成「一块投给一屋子人看的板」，然后按这个前提排优先级。
**这个前提只对了一半，是本次审查里最需要纠正的一条。**

白板实际有**两个模式**，而且现在一个都不是显式的——靠用户自己拉窗口大小去凑：

| | 演示态（像 PPT 放映） | 整理态（像 PPT 编辑） |
|---|---|---|
| **什么时候** | 会中，把当前这场的内容投给屋里所有人 | 会后，逐字稿和 AI 框架都齐了，人要整理出结论 |
| **谁在看** | 一屋子人（后排也要看得清） | 一个人（要看得细、要能改） |
| **主要动作** | 只读、翻档 | 读 + 改 + 决定留什么 |
| **对界面的要求** | 字号、对比度、缩放、全屏 | 编辑、检索、导出、来源可辨 |
| **现在的支持** | 完全没有（无字号档、无缩放、无演示模式） | 部分（有编辑器、有阅读/编辑开关） |

**证据** 白板窗口默认开 900×650，这个宽度落在「窄屏」那一档（侧边栏阈值是 1000px），
打开时跟随最新一场、默认停在阅读态、默认显示 AI 那一档——**默认形态其实是整理态**。
投屏要用户自己把窗口拉到全屏，而拉大之后**什么都没变**（字号是写死的 13px），等于投屏时反而更难看清。

**这条对前面几项判断的影响**：可读性问题是**演示态专属**的，不该当成全局最高优先；
而"人的判断怎么进来"（下一节）属于整理态，也不能和演示需求混着排。**两个模式必须先分开。**

## 三、人的判断怎么进来（Granola 那个问题）

参考的 Granola 不是「逐字稿 → AI」的单向管道，中间有人的手在。它的三种人工输入在 RTC 里的对应关系：

| 时机 | 人给什么 | 对 AI 的作用 | RTC 现在通不通 |
|---|---|---|---|
| 会前 | 背景、目标、角色、边界 | 规定分析视角（事前引导） | **断了**——字段还在、保存动作还在，但入口被收起且没有任何按钮能打开 |
| 会中 | 「这里重要」「这个待办」 | 标出真正重要的内容（分析锚点） | **没有**——能力完全不存在 |
| 会后 | 补写、纠正、删改 | 校正结果（人审） | 通着（白板正文可编辑） |

**所以答案是：不是"再做一个 AI 功能"，而是把三条人的通道补齐，AI 只负责补证据。**

### 我建议的形态

**会中锚点**——这是唯一真正缺失、也最关键的一条：

- 采集点必须在**录音那个界面**，不能在白板窗口。会中你在主界面开着录音，不可能切窗口去打字。
- 锚点存成**和逐字稿同一条时间轴上的一个条目**（时刻 + 可选一句人话），不是另建一个数据库。
  这样"依据"是天然成立的：AI 引用结论时能回指到「你当时在这里标的点」。
- 它必须是**旁路**，不许挡主流程（产品原则 4）：标不标都不影响录音和出字；AI 不可用时锚点也照存，
  因为它就是普通文件里的一行（产品原则 5）。

**会前定义**——入口要恢复，但**位置和形态要重新决定**（见 B-03），不能简单地把旧面板放回来。

**一条对称的观察**：我们要给这个项目建的"判断台账"（本文），和产品里"人的判断怎么进来"，
**是同一个形状**——人给锚点和裁决，AI 补证据和结构。做本文这套四档的过程，本身就是那个产品功能的
最小可用版本。这不是巧合，值得记一笔。

## 四、判断台账

编号 `MB-`（Meeting Board）在本文内唯一。**已存在 UX 编号的条目直接引用，不重复记。**

### A 档 ｜ 接收（依据明确，可以排期）

**MB-01 会中锚点：让开会的人能说「这里重要」**
- 依据：Granola 结论（人的现场判断是产物质量的分水岭）+ 用户本次明确把这个问题提了出来 + 项目创新清单 P1 第 1 条。
- 边界：只做「打点 + 存下来 + 交给外部分析当锚点」，**不做**重点的自动识别、不做第三块笔记区。
- 前置：采集入口的形态要先真机试手感（见 MB-17），但**这件事本身已经可以排期**。

**MB-02 逐字稿的时间必须是真实时刻**
- 依据：已实测（`ux-issue-log.md` UX-2 的对照表：真实都在 21:04 的三条被显示成 21:04/21:05/21:06）；违反了产品原则 2 和 3。
- 边界：只修时间来源；**同分钟如何显示**是另一个问题（见 MB-12）。

**MB-03 外部 AI 写进来的内容不能被用户这边悄悄盖掉**
- 依据：项目方向文档《还没做完的》第一条自己确认；产品原则 6 的镜像（原则讲的是"用户改的不能被覆盖"，反过来同样成立）。
- 边界：只做"保存前先确认底本动过没有 + 命中就提示"，**不做**自动合并。

**MB-04 后台正在整理时，白板要说「正在整理」**
- 依据：`ux-issue-log.md` UX-8（服务端已区分处理中，前端没认）；违反产品原则 3。
- 边界：只改状态来源，不动整理逻辑。

**MB-05 空着的时候不要露出编辑器的骨架**
- 依据：`ux-issue-log.md` UX-5（实测到了「无标题」和「目录 0」的元素与尺寸）。
- 边界：只在**没有内容**时生效；有内容时那条"编辑器挂载要能量到高度"的约束仍然成立，不许一并删掉。

**MB-06 白板要有显式的「演示态」**
- 依据：第二节的两个模式；UI 规范第 1 节自己写着"白板是要投给会议室里所有人看的"。
- 边界：字号档 / 缩放 / 一键全屏，**不重做一套界面**。演示态只读。

### B 档 ｜ 待裁决（要一个产品决定，实现方不能自己定）

**MB-11 「次要文字很淡」到底算不算毛病**
- 现象成立（UX-3 实测 48 处低于 4.5:1，白板 2.42:1，主界面 3.13:1）。
- 要决定的：**4.5:1 这条线在本项目算不算数。** 算，就把淡色系列整体调深一档；不算，就写进规范说它不适用，并把 UX-3 标成已否决。**不能两边都要。**
- 我的倾向：算数——因为演示态要投屏，淡色在投影仪上是真的看不见。但这是产品决定，不替用户拍。

**MB-12 逐字稿里同一分钟连着几句，时间怎么标**
- 修完真实时刻后必然出现（三条都显示 `[21:04]`）。
- 要决定的：接受重复，还是"间隔超过 N 分钟才标一次时间"（像微信那种居中时间分组）。
- 我的倾向：后者，和产品里已有的时间分组习惯一致。

**MB-13 白板要不要一直保持纯白**
- 现象成立（`ux-issue-log.md` UX-4：89 处颜色写死、共享调色板一处没用、多了一个黄色强调色）。
- 要决定的：① 纯白是"投屏要的高对比"还是"就是没接调色板"；② 那个黄色强调色留不留。
- 我的倾向：**演示态纯白、整理态接回纸色**——这样两个模式的存在正好给这个问题一个答案。但需要用户确认。

**MB-14 逐字稿里那个「编辑」按钮忽隐忽现要不要治**
- `ux-issue-log.md` UX-9，原评级就是"低"。
- 要决定的：值不值得为它改一次（改成变灰而不是消失，或者干脆把只读提示换个位置）。

### C 档 ｜ 否定（前提站不住，或刻意为之）

**MB-21 【否定】「白板的第一身份是投屏工具，所以可读性是最高优先」**
- **这是本次被推翻的一条**。投屏是一个模式，不是默认身份；默认形态（900×650、只读、跟随最新一场）更像整理态。
- 后果：可读性问题的优先级**从"全局最高"降为"演示态内最高"**，靠 MB-06 解决，而不是把整块白板的字号统一调大。

**MB-22 【否定】「会前定义的入口被焊死，要马上恢复」**
- 前提站不住：如果整理态是主场景，定义的价值要重新算——它服务的是"AI 按什么角度看"，不是"人怎么整理"。
- 处置：降级成 MB-03 的一部分，等两个模式定下来再决定入口放哪、放什么。

**MB-23 【否定】「马上给这些发现新增 UX 编号」**
- 本次**不新增**。现象层账本（`ux-issue-log.md`）里已经有 UX-2/3/4/5/6/8/9 对应的条目，重复记一遍只会让同一个毛病有两处状态、两处会不一致。
- 本次真正的产出是**判断层**（本文），不是现象层。

**MB-24 【否定】「把 Project-Ledger 整套接进 RTC」**
- 理由：它会在 RTC 现有入口（`docs/README.md` 索引 + `ux-issue-log.md` 的状态约定）之外**再建一套并行入口和索引**，命中团队规则里"新增命名与结构先对齐已有规范、不另起一套"。
- 处置：**取它的记录格式，不取它的目录。** 本文的四档 + 元数据词汇就是从它借来的；
  将来 RTC 真需要 `context` / `trace` / `review` 这些能力时，本文的条目可以逐条转成 record-v1，成本很低。

### D 档 ｜ 缺信息（现在判断不了，先进来排队）

**MB-31 真实使用里「投屏」和「会后整理」各占多少？**
- 缺的事实：两个场景的实际比例。
- **决定了什么**：MB-06（演示态）和 MB-01（会中锚点）谁先做，以及 MB-11/13 的优先级。
- 怎么拿到：见 MB-32 的测量；也可以直接问用户。

**MB-32 会后整理这件事，真的发生过吗？**
- 缺的事实：白板正文被编辑 / 被外部 AI 写入的真实次数和时间分布。
- 怎么拿到：**可以测**——查白板文档的写入历史（什么时候写的、写的人是自己还是外部 AI、写完有没有再被改）。
- 为什么重要：如果整理态根本没人用过，第二节的整个前提就要重估；如果用过，这份数据直接给出优先级。

**MB-33 AI 写进白板的内容，被人改掉过多少？**
- 缺的事实：AI 正文与最终正文的差异量。
- 怎么拿到：**可以测**——对比同一场的 AI 写回版本和最终保存版本。
- 为什么重要：它验证的是"用户会把模型的推测误认成自己的判断"这个风险（本文新写进规则库的 `PRD.ATTRIBUTION.001`）是不是**真实存在**。如果基本没人改，说明风险低；如果改得很多，说明来源标记该做。

**MB-34 会中打点会不会干扰开会？**
- 缺的事实：真机上的手感与干扰程度。
- 怎么拿到：只能真机试。先做最轻的入口（一个按钮 / 一个键），观察会不会被误触、会不会打断说话。

## 五、被我自己推翻的判断（留痕）

这次审查里改了主意的，单独记一笔，因为**"原来为什么那么想"比结论更容易被下一个读的人误当成对的**：

1. **「白板是投屏用的」** → 改为「白板有两个模式，投屏只是其中一个，而且不是默认那个」。
   触发这个改动的，是用户指出「会后要整理、要看输出哪些结论」这件事同样重要。
2. **「会中打点的入口可以放在白板窗口」** → 改为「必须在录音那个界面」。
   理由是投屏场景下人不切窗口；这是这条能不能做成的关键，也是原来没做的真实原因。
3. **「先引入 Project-Ledger 做结构化」** → 改为「借它的格式，落到 RTC 自己的 docs 里」。

## 附录：给工程看的线索（产品同学不用看）

- **MB-01 会中锚点**：事件写入目前只接受 `type:'segment'`（`server.js` `POST /api/transcripts/events`），需要新增事件类型；入口可复用 `src/js/commands.js` 的 `runActionCommand()` / `ACTION_LABELS`；全局热键机制参考 `src-tauri/src/lib.rs:776`（⌥⌘P）。
- **MB-02 逐字稿时间**：根因在 `server.js` 的 `detectSessions` 把事件压成 `texts: string[]`，`ev.ts` 在这一步丢了；`formatTranscriptLines`（`server.js:1046-1058`）只能按序号插值。
- **MB-03 反向冲突**：`PUT /api/meeting-board/document` 需要改成带 `base` 的条件写；上游 Omia 的 `createSourceConflict` 可参考。用户侧自动保存在 `meeting-board/src/main.js` 的 `saveDoc`（停手 400ms 触发）。
- **MB-04 整理中状态**：`preliminaryPending` 是页面局部变量（`main.js`）；服务端 `preliminary.status` 已有 `pending`，`meeting-board/src/lib/preliminaryPanel.js` 的 `resolveTabView` 可以直接吃。
- **MB-05 空态骨架**：上游空文档的占位元素是 `.omia-page-title-placeholder` 与大纲入口；注意空态与"有内容态"的 `visibility` 约束不同，别一刀切。
- **MB-06 演示态**：`meeting-board/src/style.css` 里 `.board-pane pre{ font-size:13px }` 是写死的；全局搜不到任何 zoom / fullscreen。窗口开在 `src/js/main.js` 的 `meetingBoardBtn.onclick`（900×650）；宽屏阈值 `WIDE_MEDIA` 在 `meeting-board/src/main.js` 与 `style.css` 各有一份，改的时候要同步。
- **MB-11 对比度**：白板 `.preliminary-note` 是 `#6f6860`；主界面 `--ink-faint` 是 `#8f8572`。量具是 `npm run check:ux`（需要 Playwright，不在仓库依赖里）。
- **MB-13 配色**：白板是独立 HTML 入口，不加载主界面的 `:root` 调色板；黄色强调色用在 `fallback` 态（`.preliminary-panel[data-state="fallback"]`）。
- **MB-32 / MB-33 测量口径**：白板数据在应用数据目录的 `meeting-board.json`（`definition` / `document` / `analysis`）；逐字稿事件在 `events/YYYY-MM-DD.jsonl`。对 `document` 做版本与时间分布统计即可；MB-33 需要同时取到 `analysis`（AI 写回那版）与最终 `document`（`rtc board show <场次ID> --json` 一次就能拿到）。
- **新增的两条规则**：`PRD.PROJECTION.001`（投给一屋子人看的界面，可读性是功能项不是审美项）、`PRD.ATTRIBUTION.001`（人与 AI 写在同一份产物里时，AI 补的内容必须能被认出来）。两条都在试用期，用不上就 `ec rules log <ID> --result fail` 把它压下去。
