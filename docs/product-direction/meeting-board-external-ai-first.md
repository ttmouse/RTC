# 会议白板：外部人工智能优先路线

## 一句话

应用负责记录、保存、动态加载和展示；外部人工智能负责理解会议、生成分析并写回文件。

## 为什么分阶段

先验证「会议记录 → 外部分析 → 白板展示 → 人工修正 → 文件保存」这条闭环，再考虑把稳定能力放回应用内部。这样可以先验证产品结构和数据格式，不提前绑定模型、服务商和调用方式。

## 当前阶段的边界

### 应用内部做什么

- 接收并保存逐字稿
- 读取白板数据
- 每 2 秒检查最新结果
- 展示会议定义和最新分析
- 提供 Markdown 白板编辑
- 保存人工编辑内容
- 使用本地 Ollama `minicpm5-meeting` 生成旁路的初步整理

### 外部人工智能做什么

- 推断会议背景、目标、角色和边界
- 分析当前话题、结论、待决问题和行动项
- 生成会议纪要
- 将结构化结果写入白板接口

初步整理（本地 Ollama 模型）和外部 AI agent **写的是同一样东西**：AI 会议内容，也就是白板正文 `document`。区别只是谁先写、谁更聪明：本地模型在会中先垫一版并随转写更新，更聪明的 agent 之后整篇替换。两者都不修改原始转写事件。

写入边界（`runPreliminary整理` 里那段「正文还归本地模型所有吗」）：

- 整理成功 → 写进 `document`，白板立刻有内容可看。
- 只在正文**是空的**、或**还等于上一次本地模型的输出**时写。
- 用户手改过、或 agent 写过 → 到此为止，不再覆盖——那是别人的成果。
- 整理失败（`fallback`）→ 只记录原文用于展示，**不写** `document`。

**白板底层只有两部分内容**：`逐字稿` 和 `AI 识别的内容`。**AI 识别的内容就是白板正文本身**——不是另有一块「笔记区」跟它并列。每场会议因此只有这两样东西。

对应到界面上就是**两个标签，共占标签下面那一整块位置**：

- `逐字稿`：ASR 原话，只读。来自 `/api/meeting-board/definition` 的 `transcript` 字段（现读 events，每行 `[HH:MM] 内容`），不落盘、不参与保存。
- `AI 识别的内容`：**编辑器本身**。它显示的就是白板正文（`document`），可以直接改。本地模型和外部 agent 都往这一份里写；正文正好等于本地模型那一版时内部标成 `local`。
  **但出处不在界面上念**：这一档只要**有内容就只给内容**，不写「可直接编辑」「本地模型 · <模型名>」这类自我说明（2026-09-17 用户明确要求，见 `../product-rules/ux-issue-log.md` UX-10）。出处标出来是为了让程序取对正文，不是为了展示。

两条当年被明确纠正过的规则，别退回：

- **标签下面只有一块内容。** 不存在「标签区 + 内容区 + 笔记区」三层，也不存在标签下面另起的第二块编辑器。
- **默认档由内容决定**：AI 那档有内容就看它，没有就落到逐字稿——任何时候都不给一个空面板让人等模型。**但用户手动点过的档要照做**，哪怕它是空的；空的 AI 档会自己说清是「生成中 / 生成失败 / 还没有」并指路逐字稿。用自动回落把用户的点击吃掉，等于告诉他这个标签是坏的。选择记在 `localStorage`。
- 陷阱是 `fallback`：那时 `preliminary.text` 存的就是原文（服务端把 transcript 抄了进去），所以「有 preliminary」不等于「有 AI 稿」，这一档必须如实说生成失败，不能让原文冒充结论。说明文字写在**内容区底部**（`.preliminary-note`），不写在标签栏；**有内容时那一行是空的、连元素一起藏掉**。

AI 那一档正文的优先级：已保存的白板正文 > 外部分析生成的那版 > 本地模型那一版。越靠前越「最终」。判定逻辑在 `meeting-board/src/lib/preliminaryPanel.js`，是纯函数、有测试（`tests/preliminary-panel.test.mjs`）。DOM 只负责把结果塞进去。

**布局**：整页锁在一屏高，顶栏一行会议名，下面是标签栏 + 一整块内容区。两条几何约束，单测看不出来，要用浏览器量：

1. **不做成「电梯」**：内容区铺满可用高度，不要固定高度的小滚动框。
2. **不做成上下两块**：两档各占满同一块位置，切换是换内容（非当前档用 `visibility:hidden` 藏，保留布局——编辑器挂载时要量高度，`display:none` 会量到零）。

验证方式：顶栏之下应只有 `.preliminary-panel` 一段，且 `.editor-wrap` 在它**内部**；两档切换不改内容区的位置和高度。

## 文件数据结构

白板数据暂时存放在应用数据目录的 `meeting-board.json`，包含：

- `definition`：会议定义
- `document`：人工维护的 Markdown 正文
- `analysis`：外部人工智能生成的最新结构化分析

后续稳定后可以拆为多个文件，但第一阶段先保持一个文件，便于验证闭环。

## 外部写入方式

外部 AI 与白板之间只有一条通道：`rtc board`（脚本本体是 `scripts/meeting-board.mjs`）。
「把这场会议的记录写进白板」是三步：

```text
rtc board brief                            # 拿材料：会前定义 + 该场逐字稿 + 已有正文 + 写回格式
                                           # 中间：分析，产出 结果.json + 正文.md
rtc board write-analysis <结果.json>        # 结构化结果（写进 analysis）
rtc board write-document <正文.md>          # 正文，这才是用户在面板里看到的东西
```

两个必须记住的点：

- **只写 analysis，白板不会变。** 面板只渲染正文，analysis 只在该场正文为空时被用来生成一版正文。
- **`write-document` 是整篇替换。** 要保留已有正文就加 `--append`（新内容接在后面）；
  整篇替换一个非空正文时 CLI 会在 stderr 提醒一次。`brief` 会把已有正文整段打出来，方便合并。

`brief` 把外部 AI 需要的东西一次给全（定义、逐字稿、已有正文、要写哪些字段、写回命令），
外部 AI 不需要自己拼上下文，也不需要先问一遍场次编号。
Agent 侧的一站式说明书沉淀在 `~/.agents/skills/rtc-meeting-board/SKILL.md`。

其余子命令：

```text
rtc board sessions [--date D]     当天场次列表（* 标出最近一场，并显示哪些已有分析）
rtc board latest [--date D]       最近一场的场次 ID（纯文本，可喂给别的命令）
rtc board transcript [场次ID]     该场逐字稿
rtc board show [场次ID] [--json]  该场已保存的定义 / 分析 / 正文
rtc board write-definition <JSON> [场次ID]
rtc board write-document <Markdown> [场次ID] [--append]
```

场次 ID 省略时默认取「最近一场」。给了 ID 时由 ID 反推日期再定位，
所以隔天也能直接补写前一天的会议，不用先查是哪一天。

读的部分直接读本地文件（应用没开也能用）；写回走本地服务，由服务端串行合并。
底层接口仍在：`PUT /api/meeting-board/analysis|definition|document`。

## 面板行为

白板打开时会按本地日期和连续转写之间的静默间隔整理会议场次：静默超过 5 分钟，就视为进入下一场会议。场次按钮显示在白板顶部，点开是一个**搜索框 + 场次列表**的下拉，可以切换不同会议。

**下拉是跨天的。** 不带关键词时给的是「最近若干场」（跨天，最新在前），输入关键词则按
标题 / 逐字稿 / 已保存正文检索全部历史——不然历史会议根本没有入口（`/sessions` 只看今天）。
检索走后端 `GET /api/meeting-board/search`，返回里带一句命中的逐字稿做上下文，让人看得出
「这场为什么会被搜出来」。

历史场次的**标题必须带日期**（`9月16日 · 会议 11:41`）：同一天里「会议 11:41」是唯一的，
跨天就不再唯一，不带日期就分不出自己在看哪一天。今天则不加日期，全是今天时那只是噪音。

还有一个必须守住的边界：**只有选中「今天」的场次时才做自动跟随**。原来的规则是「选中的场次
不在列表里就退回最新一场」，看历史会议时它当然不在今天的列表里——照旧执行就会每 2 秒把人
踢回今天。所以选中的场次属于哪一天要跟着一起记（`meeting-board/src/main.js` 的 `selectedDate`）。

白板打开时先读取已有数据，之后每 2 秒去拉一次**当天的场次列表和当前场次的正文及初步整理**。当场次内容新增时，后台通过 `POST /api/meeting-board/preliminary?sessionId=...` 触发本地 Ollama；同一份转写按内容指纹缓存，进行中的请求也只保留一份。
「当天」是权威列表：轮询它才知道今天有没有新场次。下拉里显示的那一份（检索结果）与它分开存，
拿检索结果去判断「今天的场次变了没有」会永远判成变了。

外部写完正文后，面板会自己重读 —— 不用切会议、不用重开窗口，也不用刷新应用。
这个行为移植自 xiaoer-omia（`src/lib/fileDocumentDraft.ts` 的 `resolveExternalFileChange` /
`sourceContentFingerprint`）：换文档必须整个重挂编辑器（Milkdown 的文档值是初始化参数），
但什么时候该重挂是有规则的（`meeting-board/src/lib/externalRefresh.js`）：

| 情况 | 行为 |
|------|------|
| 内容指纹没变 | 什么都不做。少了这条，轮询会把正在看的文档每 2 秒重挂一次，光标和滚动一直跳 |
| 指纹变了、本地没改动 | 重读，面板变成磁盘上的那份 |
| 指纹变了、本地有未保存的改动 | 不覆盖，只提示「你这边有没保存的改动」，用户的内容优先 |

指纹是 FNV-1a 32（内容 + 字节数，和 Omia 同算法同格式），只用来判「底本换没换」，不是安全哈希。
窗口重新拿回焦点时也会多读一次。

另一件需要知道的事：面板只渲染 `document`（正文）。`analysis` 不单独展示，
只在该场正文还是空的时候被用来生成一版正文；正文一旦有内容，写 analysis 不会再改正文。
所以外部 AI 一次完整的更新要同时写 analysis（结构化）和 document（人看的）。

外部工具写入指定会议时，在文件后追加场次编号：

```text
rtc board write-analysis <分析结果.json> <会议场次ID>
```

场次编号由 `rtc board sessions` 或面板接口 `GET /api/meeting-board/sessions?date=YYYY-MM-DD` 返回。

## 后续阶段

1. 用真实会议记录验证外部分析结果。
2. 验证分析文件变化能稳定反映到白板。
3. 增加分析结果版本和来源标识。
4. 将人工正文、原始转写、分析结果拆成独立文件。
5. 只有重复、稳定、边界明确的能力，才评估是否内置人工智能。

## 验收标准

- 应用内没有主动人工智能调用。
- 外部写完正文后，已打开的面板自己重读（不切会议、不重开窗口）—— ✅ 已实现并有验证脚本。
- 内容没变时不重挂编辑器（不闪、不丢光标）—— ✅ 已实现并有验证脚本。
- 人工编辑正文不会被自动刷新覆盖 ✅（编辑时的自动保存会不会反过来盖掉外部写入，见下）。
- 重启应用后，定义、正文和分析结果仍然存在。
- 没有配置人工智能服务时，白板仍然可以正常打开和编辑。

验证脚本（不占端口、不碰真实数据，临时数据目录 + WebKit）：`/tmp/rtc-board-reload-test.py`。
它要的东西：一个 `RTC_DATA_DIR` 指向临时目录、监听 8997 的 server.js、以及装了 Playwright 的 python。

### 还没做完的

- **反向的一半没有保险**：用户这边的自动保存（停手 400ms 后触发）不会先确认磁盘是否被外部改过，
  所以如果外部的写入刚好落在用户敲字之后，用户那份会把外部刚写的内容盖掉，且没有提示。
  Omia 在保存侧也有一个冲突检查（`createSourceConflict`），这边还没做。要做的话建议顺手把服务端
  的 `PUT /api/meeting-board/document` 改成带 `base` 的条件写，否则两边同时写仍有窗口。
- 编辑器的 `onChange` 是滞后的（实测合成按键连续敲 2.7 秒都没回调，下一次输入才把上一次的内容交出来），
  上面那条「本地有改动就不覆盖」的保险准不准，取决于它什么时候把内容交出来。这个要等编辑器那层稳定后再验。
