# 设计治理合同

这份合同回答三个问题：**改视觉要走什么流程、要拿什么证据、谁裁决冲突。**

它不重复规则本身：规则在 [DESIGN.md](DESIGN.md)（单一正本，2026-09-30 由原 visual-language 与 design-principles 并入），
问题台账在 [`../product-rules/ux-issue-log.md`](../product-rules/ux-issue-log.md)。

## 1. 范围

- **适用**：颜色、字体、字号、间距、圆角、图标、动效、浮层、新窗口/新页面的外观，
  以及任何会进入用户眼睛的实现细节。
- **不适用**：交互流程与状态机（`ui-interaction-spec.md`）、数据结构与端口（`../architecture/`）、
  安装与打包步骤（仓库根 `README.md`）。

## 2. 四种真相，各有各的位置

| 位置 | 回答 | 冲突时 |
|---|---|---|
| `src/css/style.css` 的 `:root` 与 `tray.js` | 数值**实际**是多少 | 它是数值的唯一来源 |
| 本目录（正本 + 原则） | 应该长什么样、为什么 | 与代码不一致就是缺陷，两边都要改 |
| `ux-issue-log.md` | 已经发生过什么、修没修 | 只记账，不定义规则 |
| `../evidence/` | 某次改动实际检查了什么 | 只证明那次，不升级为规则 |

发现「文档说要这样、代码是那样」时：**不要悄悄选一边**。按本文第 4 节登记，再改。

## 3. 改动分级与证据

| 级别 | 什么算 | 必须给的证据 |
|---|---|---|
| **A 级：token 与全局规则** | 改 `:root` 的任何值、改共用规则（图标盒模型）、改强调色使用范围 | `npm test` + `npm run check:ux`（对比度与几何是真量出来的）+ **真机看过主界面**；涉及菜单栏还要看菜单栏 |
| **B 级：单组件/单页面样式** | 调一个组件的内距、字号、悬停色 | `npm test` + `npm run check:ux`；改了列表或浮层还要真机滚一次 |
| **C 级：新增独立表面** | 新窗口、新页面、新的样式入口（如白板那样） | 上述全部 + 在待裁决登记里留一行 + 用户确认 |

三条固定门禁（都可直接跑）：

```bash
npm test            # 文档门禁 + 静态检查 + 全部自动测试
npm run check:ux    # 真浏览器量几何与对比度（容器裁切、遮挡、可点区域、对比度、横向溢出）
npm run check:audio # 录音链路（改动涉及音频会话/麦克风时）
```

前置：`check:ux` 需要 Playwright 的浏览器（`npx playwright install chromium`）。
2026-09-20 盘点时本机缺这个浏览器，该步未运行——**没跑成就是没验过**，
当时的对比度结论只能引 2026-09-17 的历史实测。

**软件层面的判定优先于人工描述**：能写进 `check-ux.mjs` 的判据就写进去，
写不进去的（手感、气质、动效是否说谎）必须在真机上由人看过——并且要在记录里写明是人工结论。

**注意 `check:ux` 验的是 `dist/meeting-board`**：改白板后必须先 `vite build`，
否则量的是旧构建（这条踩过）。

## 5. 批准边界

- **Agent 可以自行改**：把写死色值换成已有 token、把新组件并进既有共用规则、
  修不达标的对比度与可点区域（这些是往规则收敛，不改变视觉意图）。
- **必须由用户拍板**：改 token 的值、引入第二种强调色、新增大圆角/渐变/阴影、
  给新表面独立外观、接受某个对比度不达标。
- **判断依据**：这条改动会不会改变用户看到的**结果**？会，就归第二类。

## 6. 回退

- 样式改动集中在 `src/css/style.css` 与 `meeting-board/src/style.css` 两个文件，
  单文件回退即可；涉及菜单栏时还有 `src/js/tray.js` 与 `src-tauri/src/lib.rs` 的 `TRAY_WIDTH`。
- 改 token 后回退必须**重跑** `npm run check:ux`：对比度是算出来的，
  不能凭「改回去了」当成没发生。
- 回退同样要按 [证据规范](../evidence/README.md) 留一条记录（写明回退原因与重测结果）。
