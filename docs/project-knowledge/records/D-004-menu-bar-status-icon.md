## 为什么

用户（产品侧）提出的问题：**典型用法是把本窗口丢在别的软件后面一边说话一边等字出来，
这时候看不到底部状态区**——「正在识别」恰恰是他最需要不用切换窗口就知道的事。
此前 macOS 只有 Dock 图标，没有菜单栏出口，用户只能切回来瞧一眼。

定下来的四件事（不是实现细节，是「不许顺手改」的部分）：

1. **内容只来自主界面那一次状态判断**（`src/js/ui.js` 的 `computeRunStatus`）。
   菜单栏不重新判断状态，只做「结论 → 字形/文字」的翻译。菜单栏和主界面说两套话，
   比没有菜单栏更糟。
2. **四个字形，语义各自成立**（资源在 `src-tauri/icons/tray/`，Lucide 图标 ISC 协议，
   纯黑 + 透明的模板图，由 macOS 按明暗着色）：
   空心麦克风＝就绪、实心麦克风＝在录、带斜杠的麦克风＝输入侧坏了、警告三角＝服务侧坏了。
   **图标不许和文字说相反的话**，所以输入侧和服务侧分开两个字形。
3. **空闲一个字都不写**（菜单栏寸土寸金）；在录写「识别中 00:07」——
   时长不是装饰，静止的两个字看不出程序是活的还是卡住了，会跳的秒数才是「还在动」的证据，
   而且它和主界面状态区用的是同一个值。
4. **点击图标只做一件事：把主界面拿到前面**（含 ⌘H 隐藏过的情形）。**不做第二套菜单**：
   图标只回答「在不在工作」，具体原因和下一步在主界面里。

看过的方案：给菜单栏挂一个下拉菜单（打开窗口 / 开始录音 / 设置 / 退出）——被否，
同一个状态会在两个地方各说一遍，而且图标会从「状态」退化成「又一个入口集合」。
彩色图标（红色录音点）也被否：与第 1 节的「纸和墨」冲突，且模板图能跟着系统明暗走。

人被读的那份（产品语言、含「不要做」）在 `docs/product-rules/ui-interaction-spec.md`
第 2 节「菜单栏图标」——**本记录不复制它的正文，只承担 id、来源、关系与「当时怎么判断」的存档**。

## 2026-09-19 当天追加：把录音时长换成「说话中」

用户看到第一版（`识别中 01:56`）后直接反馈：**时长对他没有价值**——他不说话时那个数字也在跑；
他要知道的是「当前我正在说话，它检测到音量、而且音量符合要求」。

据此改了两处：

1. **录音时长从菜单栏揭掉**（主界面状态区照旧显示，那里本来就有）。
2. **新增第五种说法「说话中」**，由 VAD 的结论（`state.vadState`）驱动；
   说话时图标同时从实心麦克风换成电平柱（不读字也能一眼看到）。
   判据就是用户说的那件事：音量收到了、而且过了自适应门槛（见 `src/js/asr.js` 的 `vadSend`）。
   说完后连续约 0.85 秒低于门槛才退回「识别中」（`VAD_SILENCE_BLOCKS`），
   句间呼吸停顿不让字闪。

两个必须一起改的点，否则功能会以为做好了其实没做：

- **`updateSpeechState` 里状态翻转的那两处必须立刻调 `renderRunStatus()`**。平时状态区是一秒一轮，
  等轮询的话——用户说完半句话菜单栏才变，那就失去了意义。
- **优先级**：异常和「正在连接」压倒「说话中」。出事时不许被一个「听到声音」盖过去；
  录音中服务还在连时说「正在连接」，因为用户需要知道卡在哪。

为什么不算「菜单栏自己在造状态」：主界面对同一件事的表达是**电平尺**（条子随音量跳），
菜单栏没地方放尺子，就用一个字幕代替——同一件事的两种表达，不是两套判断。

### 当天追加之二：起说门槛 + 「已听到」回执 + 一声柔和提示音

用户接着提了三件事，每一件都改了：

1. **不能「一过门槛就亮」，要连一会儿才算**。否则一瞬的噪声（敲键盘、碰一下麦克风、鼠标点击、
   桌椅响）就能让菜单栏闪一下。落地为 `VAD_ONSET_BLOCKS = 3`（音频回调约 11.7 次/秒，
   3 块 ≈ 0.26 秒墙钟、真实音频约 85ms；中间掉一块就从头数，所以爆音连不起来）。
   **为什么不是更长**：真要挡住一秒的关门声，代价是说话后近一秒菜单栏才变，得不偿失。
   与结束侧 `VAD_SILENCE_BLOCKS = 10`（约 0.85 秒）共同构成短押。
2. **说完之后给一个「已听到」回执**（`HEARD_GRACE_MS = 1200`）：字没了但电平柱多留一小会儿。
   理由是用户关心的其实是「我的话被听到了吗」——一停下就什么都没了，回馈就变成「没了」。
   计时从**最近一次确认说话**算，不是从起说算（否则说完一个 30 秒长句时时间戳早过期，回执永远不出现）。
   **也不能每块大声都刷新**：那样一次 85ms 噪声也会换来 1.2 秒回执——正是要避开的闪烁。
3. **起说时给一声柔和提示音**（`sfx.js` 的 `playHeard`）。第一版是 880Hz 三角波、12ms 起音、
   50ms 结束，用户听完否了：**太轻，而且「声音的方式」不喜欢**——三个原因凑成那个「点击感」
   （三角波有奇次谐波、12ms 起音太陡、50ms 会被听成瞬态而不是音调）。
   改成 **740Hz 正弦 + 45ms 起音 + 200ms 衰减 + 峰值 0.11**（正弦无谐波最柔，慢起音去点击感，
   尾巴长到能听成一个音；峰值从 0.05 提到 0.11 约 +7dB）。
   `note()` 因此多了一个 `attack` 参数（默认 12ms，其余提示音不变）。

### 当天追加之三：提示音整个撤掉

第二版（740Hz 正弦、慢起音）用户听完仍然否了：「现在那个触发的音效声音太明显了，把音效移除掉吧」。
**结论：起说时不响任何声音**，只留菜单栏的电平柱 + 「说话中」。

关键是这次的原因不是「不够柔」——两版的柔和度已经到位了，问题在**频次**：
这一声每句话开头都会响，一段话里每句都被打断一次，存在感迅速盖过它携带的信息。
而它想回答的问题（我的话被听到了吗）菜单位已经在答：那片区域**永久可见、不占听觉**；
提示音占的却是听觉，而一个会反复响的东西比一块常驻像素贵得多。
再加上麦克风此时在采集，提示音本身有被录进转写的风险（靠 EchoCancellation 抵消，
用户关掉降噪时就失效）。

撤掉的包括代码本身：`playHeard` 删除，`note()` / `seq()` 的 `attack` 参数一并收回去
（没人用了就是死代码）。两版参数与上述理由留在 `src/js/sfx.js` 底部，
并在 `tests/tray-speaking.test.mjs` 里钉一条「起说不响任何音效」——想加回来的话，
得先把这行测试删掉，强制先看到当时的结论。

**提示音必须走 WebAudio，不要改成 `<audio>` 元素播放**（适用于将来任何一次“加回音效”的尝试）：
那一阵走的是另一个音频会话，`getUserMedia` 的 `echoCancellation` 管不到它，
这一声会被直接录进转写。

### 当天追加之四：去掉全部文字，改用颜色

用户第三轮的要求：**「把 icon 边上的文本都去掉，默认状态文本也不需要了」+「这个 icon 的颜色能不能换一个，
比如说橙色」**。

两件事都做了，而且它们其实是同一个方向：**把那一格从「一行字」变成「一个信号」**。

1. **菜单栏不再有任何文字**（`trayView` 不再返回 title，`set_tray_status` 不再有 title 参数，
   连 `set_title` 都不再调用）。要看具体的字、原因和下一步，悬停有 tooltip，点开就是主界面。
2. **颜色成为新的信号**，并且**只在有话说时出现**：

   | 状态 | 字形 | 颜色 |
   | --- | --- | --- |
   | 没在录 | 空心麦克风 | 黑白（跟随系统明暗） |
   | 在录但安静 | 实心麦克风 | 黑白 |
   | 正在说话 | 电平柱 | 橙 `#E8720C` |
   | 出事了 | 带斜杠的麦克风 / 警告三角 | 红 `#D93025` |

   两个决定值得记下来：

   - **橙色只绑「正在说话」**。第一版把橙色给了「在录」，用户随即纠正：**录音中不该橙，只有说话过程中才橙**。
     这条纠正是对的，理由比第一版更硬：常亮的颜色会变成背景，只有难得的颜色才是信号——
     如果「在录」也橙着，橙色就是常驻底色，真正该被看见的「我听到你说话了」反而淹没在里面。
     「在录没在录」由字形承担（空心 / 实心麦克风），信息没丢，只是换了通道。
   - **异常用红，不用橙**。橙已经表示「在录」；异常也是橙的话，「在录」就有了两种意思，
     而「出事了」反而失去自己的颜色。
   - 两个色值都按「浅底深底都看得清」挑（浅底约 3.6:1 / 5.0:1，深底约 5.8:1 / 4.2:1）——
     代价是彩色档不再跟随系统明暗，黑白档仍然跟随。

3. **上色不改图**：字形 PNG 本来就是黑白 alpha 遮罩，颜色由 `set_tray_status` 的 `color` 参数
   在 Rust 侧给 RGB 上色（`tint_rgba`），有色时关掉模板模式（否则 macOS 会把颜色丢掉）。
   一色一套图会变成 5×3 张，改一次颜色就得重画一遍图。

### 当天追加之五：三个状态各占一个颜色档（加蓝）

用户接着问：**「录音状态的时候，那这个 icon 怎么去区分？我希望有三个状态：软件启动但没开录音 /
开了录音但还没说话 / 正在说话」**。

问题真实存在：加四那版用「空心 / 实心麦克风」区分前两个，那是**形状**差异，在一格 18pt
的小图标上要盯着看才分得出。改成**颜色分档**：

| 状态 | 字形 | 颜色 |
| --- | --- | --- |
| ① 软件开着但没按录音 | 空心麦克风 | 黑白（跟随系统明暗） |
| ② 按了录音、还没说话 | 实心麦克风 | **蓝 `#1A73E8`** |
| ③ 正在说话 | 电平柱 | **橙 `#E8720C`** |
| 出事了 | 带斜杠的麦克风 / 警告三角 | 红 `#D93025` |

- **颜色回答「处在哪一档」，字形回答那一档里的细化**——两个通道各有分工，不再互相兼职。
- **蓝是给「在录」的**：橙已经归「正在说话」（加四时用户明确否掉「在录也橙」），
  所以第二档需要自己的颜色；红归异常。四种颜色互不借用，比「少用一个颜色」重要。
- 三个色值都按「浅底深底都看得清」挑（`src/js/tray.js` 的三个 `TONE_*` 常量），
  代价是彩色档不再跟随系统明暗，黑白那一档仍然跟随。

### 当天追加之六：用户定的最终方案——字形说「在不在录」，颜色说「有没有在说话」

用户先问「有没有差异化的 icon 来做区分？」，然后直接给了他要的三态：
**① 默认＝白麦克风　② 识别中＝白圆点（表示录音状态）　③ 说话＝橙色**。

这比加五那版（三档颜色）更好，落地时按他的分法重整成**两个通道各管一件事**：

| 状态 | 字形 | 颜色 |
| --- | --- | --- |
| ① 没在录 | **麦克风** | 黑白（跟随系统明暗） |
| ② 在录、还没说话 | **圆点**（录音灯） | 黑白 |
| ③ 正在说话 | **圆点**（同②） | **橙** |
| 出事了 | 带斜杠的麦克风 / 警告三角 | 红 |

- **为什么比上一版好**：上一版让字形也兼职说「有没有在说话」（实心麦克风 vs 电平柱），那点差别
  在 18pt 上要盯着看；现在 ① 和 ② 是**麦克风与圆点两个完全不同的东西**，一眼可辨，
  而「有没有在说话」交给颜色，同样是一眼的事。两个通道各自内部只有一个问题要回答。
- **结果比上一版更简单**：颜色从三档（黑白/蓝/橙）回到两档（橙/红）+ 黑白，字形从五个减到四个
  （`idle` / `dot` / `mic-off` / `service-error`），`live.png` 与 `speaking.png` 两个图直接删掉
  ——没有多余资产，也没有「同一个意思有两种画法」。
- `SPEAKING_GLYPH` 这个名字随之消失（说话不再换字形），改成 `RECORDING_GLYPH = 'dot'`。

### 当天追加之七：③ 用波浪（用户：那个波浪形状的更直观）

用户看完加六那版（③ = 橙色圆点）后要求：**「正在说话的过程中，用前面那个 icon，波浪形状的那个更直观」**。
于是把加六删掉的电平柱图恢复成 `speaking.png`，最终形态：

| 状态 | 字形 | 颜色 |
| --- | --- | --- |
| ① 没在录 | 麦克风 | 黑白 |
| ② 在录、还没说话 | 圆点（录音灯） | 黑白 |
| ③ 正在说话 | **波浪（电平柱）** | **橙** |
| 出事了 | 带斜杠的麦克风 / 警告三角 | 红 |

这一版把两个通道的分工理顺了，三条都留着：
**① 和 ② 靠字形分开**（麦克风 vs 圆点，两个完全不同的东西），
**③ 同时换字形和颜色**（它是这里面最该被立刻看到的一档，两个通道一起变），
**橙只给 ③**（常亮的颜色会变成背景）。字形回到 5 个（`idle`/`dot`/`speaking`/`mic-off`/`service-error`）。

### 当天追加之八：说话那档加「很亮的背景色」（橙色底块）

用户看到别的 App 的菜单栏样式后问：**「会有一个很大的很亮的背景色，这个效果能做吗？」**
做在 ③（正在说话）上——它本来就该是这里面最显眼的一档。

**做法**：菜单栏 API 没有「给项设背景色」的口子（`TrayIcon` 没有暴露 `NSStatusItem` 的样式），
所以背景是**画进图片里**的：`speaking.png` 变成一张**两色图**（橙色圆角底 + 白色波浪），
前端对它传 `color: "as-is"`，Rust 侧既不上色也不按模板渲染。

两件事必须一起改，否则效果会坏：

1. **它是唯一预先上色的字形**：`tint_rgba` 是单色替换，用它会把白柱子一起染橙、丢掉对比。
   代价是那点橙色写在 PNG 里，与 `src/js/tray.js` 的 `TONE_SPEAKING` 是两个地方，
   改颜色要一起改（Rust 侧 `tray_glyph_bytes` 的注释里写明了）。
2. **所有字形统一到 48×36 画布（= 24×18pt）**：菜单栏项的宽度是跟着图片走的。如果只有这一档
   变宽，**每次说话旁边那排图标都会被推来推去**——说话是每句话都会发生的事。所以其余四张
   都补了透明留白，画布一样宽；`cargo test --lib` 加了一条测试钉住「所有字形画布完全一致」。

### 当天追加之九：背景块的高度（用户一眼看出不对）

加八那版把色块做成 15pt 高（画布 18pt），用户随即反馈：**「录制过程中那个比较亮的状态的高度不对」**。
量下来确实矮：色块 23×15pt，比旁边那些第三方图标（约 13~16pt 的圆形状）还矮，看着像个压扁的胶囊。

改法：色块顶到 **17pt / 画布 18pt**（上下各留 0.5pt），里面的白柱子同步放大到约 12pt 高。
实测变成 **23×17pt**，竖直中心和旁边图标完全对齐（都在 y=14.75pt），视觉上才算一块「底」。

**18pt 是这套 API 的硬上限**（tray 固定把图片按高 18pt 渲染，宽度按比例算）——
想更高就只能不走图片、去设 `NSStatusItem` 的样式，而 `TrayIcon` 没有暴露那个口子。

### 当天追加之十：底块改画在系统按钮上（用户：要和系统点击高亮同高）

用户接着指出真正的参照物：**「点击过程中不是会有一个背景色吗？我希望和那个高度是一致的」**
——他要比的是 macОС 点击菜单栏项时那块高亮底。

这解释了加九为什么「看不出效果」：**tray 固定把图片按高 18pt 渲染**
（`tray-icon` 里写死 `icon_height = 18.0`），图片做出来的色块最高就 18pt；
而系统那块高亮底是按钮自己的 bounds——实测 **22pt**。差 4pt，怎么调图片都追不上。

**改法**：背景不再画进图片，改画在菜单栏项自己的按钮图层上（`paint_tray_background`，
CALayer 背景色 + 6.5pt 圆角）。高度由系统给，**天然和那块高亮一模一样**，
不用写死一个数字，换显示器/分辨率也不会错位。实测色块 **48×22pt**
（宽是按钮的宽度，本来就带左右留白；后来用户嫌宽，加十二 收窄到 28pt）。

随之而来的两个变化：

1. **柱子改成白色**（`SPEAKING_INK`）：底色是橙的，柱子必须和它拉开对比，
   不能再用「跟随系统明暗」的黑白模板（浅色菜单栏下会变成黑柱子压橙底）。
2. **橙色回到只有一处**：不再烤进 PNG，仍由 `src/js/tray.js` 的 `TONE_SPEAKING` 说了算
   （加八那版是两处，改颜色要一起改，现在这个问题没有了）。

代价：多两个直接依赖 `objc2-quartz-core` / `objc2-core-graphics`（本来就在依赖树里，只是提到直接依赖）。

### 当天追加之十一：色值 #FF9230 + 胶囊形状

用户指定了两件事：**「#FF9230 这是颜色的色值，然后两边我希望是大圆角，变成一个胶囊按钮的感觉」**。

- **颜色**：`TONE_SPEAKING` 从 `#E8720C` 改成 `#FF9230`（用户给的色值）。
- **形状**：圆角半径改成**按钮高度的一半**（`button.bounds().size.height / 2.0`）——不是写死数字，
  所以永远是个胶囊；同时设 **连续圆角**（`kCACornerCurveContinuous`，苹果自己那套 squircle），
  否则两端能看出正圆弧的硬拐点。两端全圆（宽度加十二 才收到 28pt）。

**白柱子在这个更浅的橙上对比只有约 2:1**（之前用的深橙是 3.6:1），看着会偏"淡"。
没有擅自改柱子颜色（用户只指定了底色），但把结论写进了 `SPEAKING_INK` 的注释：
真觉得糊，换一个深色（如 `#5A2A00`）就能立起来，只改一个值。

### 当天追加之十二：胶囊宽度 48pt → 28pt

用户反馈：**「现在整个胶囊的宽度有点宽」**。

把宽度从「由图片算」改成**写死一个值**（`TRAY_SLOT_WIDTH = 28.0`，用
`NSStatusItem::setLength`）。为什么不能在图片上解决：**按钮会在图片两侧各留一段内边距**
（实测比图片宽 16pt），所以缩图片调不准——真正决定这一格宽度的是状态栏项自己的 length。

同时把图形画布从 64×36 收回 36×36（18×18pt）：既然宽度写死了，画布就不需要再为「兜住宽度」
而留白；画布变宽反而会让图片超出格子。

**28pt 是这么定的**：里面的图形（波浪）约 13.5pt 宽，两侧各留约 7pt 呼吸，
看起来才像个胶囊而不是被图形撑满的长条。实测胶囊 **28×22pt**。
觉得宽窄不合适，只改 `TRAY_SLOT_WIDTH` 一个常量。

## 验证










**已核验（2026-09-19，桌面 app 实测）**：

- 应用运行时菜单栏确实出现图标，**边上没有任何文字**（多轮截图确认）。
- **三个状态都在屏幕上拍到了**：**白色圆点**（在录、还没说话）、**橙色底块 + 白色波浪**
  （正在说话，就是用户要的「很亮的背景色」效果，1 秒一张抓图里连续多张都是它）、
  **黑白空心麦克风**（没在录）；异常态的红只在合成预览里比对过，没实拍。
- **背景块没有把旁边的图标推来推去**：同一批截图里，我们右边那几个第三方的图标位置没有变化
  （画布统一的直接效果）。
- **背景块的高度量过**：色块 **23×17pt**（画布 24×18pt），竖直中心与旁边图标对齐（y≈14.75pt）。
  第一版是 23×15pt，被用户当场看出「高度不对」——这条是靠截图量像素发现的，不是靠眼看。
- 颜色真的生效（模板模式已关掉，否则 macOS 会把它重绘成黑白）；黑白档仍走模板图、
  跟随系统明暗。
- **「说话中」是跟着说话走的**：多轮 1 秒一张连续抓图里，**橙色波浪**与**白色圆点**在同一场录音里
  交替出现，不是一次性跳变。
- 这一路都是在本机默认引擎（SenseVoice）下测的，顺带证明了「本地引擎也走 `trackSpeech`」
  这条接线真的生效（漏接的话这一路永远只会停在第二档）。

**已核验（可重跑）**：

噪声断开后计数从头数、连 3 块才认）、**说完回执**（刚说完留电平柱不写字、过期后回到实心麦克风；

以及三条**源码接线断言**（本地引擎分支必须调 trackSpeech；停录时说话状态归零；
